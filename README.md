# منصة FDE — نظام التشغيل والموافقات لمصنع البيوت الجاهزة

منصة مستقلة تدير دورة **طلب المواد → عروض الأسعار → موافقة المدير العام → الدفع/العهدة → التوريد → الفحص والاستلام → فاتورة المورد → المطابقة الثلاثية → التسجيل المحاسبي في ERP**، مبنية كـ Modular Monolith قابل للربط مع أي نظام محاسبي عبر طبقة موصلات.

## المبادئ الحاكمة (مطبقة في الكود)

- **السجل مرة واحدة:** كل طلب يحمل رقماً مثل `MR-2026-000145` وترتبط به كل الأحداث.
- **المستند ليس العملية:** صورة الكوتيشن أو إيصال التحويل دليل مرفق، والحالة والاعتماد بيانات منظمة.
- **فصل الصلاحيات (SoD):** طالب المادة لا يعتمد طلبه، وطالب الدفع لا يعتمده، والمشتريات لا تعتمد السعر.
- **الموافقة مرتبطة بنسخة:** قرار المدير يوثّق `snapshot_hash` للعرض المعتمد ونسخته؛ تغيّر العرض بعدها يُبطل الاعتماد.
- **AI يقترح ولا يقرر:** منفذ الاستخراج (`MaterialRequestExtractor`) لا يخترع أكواد مواد — العنصر غير المكتشف يُعلَّم `unmapped_item` لمراجعة المشتريات.
- **لا ترحيل دون مطابقة:** الفاتورة لا تصل `READY_TO_POST` إلا بمطابقة ثلاثية ناجحة أو استثناء معتمد وموثق.
- **Idempotency لأوامر الشراء وطلبات الدفع:** إعادة إرسال الأمر المدعوم بمفتاح واحد لا تنشئ سجلاً مكرراً، والمفتاح نفسه بمحتوى مختلف يُرفض (409). لا يشمل ذلك حالياً إعادة إرسال تقارير التقدم أو صرف المواد؛ راجع حدود اختبار التصنيع قبل الاستخدام الحقيقي.
- **Exported ≠ Posted:** التصدير حزمة JSON/CSV؛ حالة `POSTED_TO_ERP` لا تُمنح إلا بعد تأكيد فعلي من النظام المالي عبر Webhook.

## البنية

تتوفر أيضاً تسوية أسعار المواد من فواتير المورد، ودفتر مصاريف مباشرة ومعدات باعتماد منفصل، وإقفال مالي بإصدارات ولقطات تكلفة ثابتة وإعادة فتح مخولة. الواجهة العربية في `/operations`، تبويب **التكلفة والإقفال**، والتفاصيل والترحيلات والقيود في `docs/financial-costing.md`.

```text
app/
├── platform/        # الإعدادات، قاعدة البيانات، الهوية والصلاحيات (RBAC)
├── shared/          # الترقيم، Idempotency، الأخطاء المشتركة
├── workflow/        # آلة حالات دورة الطلب (انتقالات معرفة فقط)
├── static/          # واجهة عربية RTL مبدئية
└── modules/         # الوحدات — كل وحدة: models + service + router
    ├── projects/            # المشروع، وحدة الإنتاج (Container/FrameCAD)، أوامر التصنيع والعمل
    ├── manufacturing/       # التصنيع والتكلفة وتسويات المواد والمصاريف والإقفال المالي
    ├── material_requests/   # طلب المادة (MR-...)
    ├── sourcing/            # حالة التسوق، العروض بنسخها، المقارنة (التكلفة المقارنة)
    ├── approvals/           # قرارات الاعتماد المرتبطة بنسخة العرض والمبلغ
    ├── purchasing/          # أمر الشراء + طلبات الدفع (دورة حياة مستقلة)
    ├── receiving/           # الاستلام GRN (كامل/جزئي/تالف/مرفوض) وفحص الجودة
    ├── accounts_payable/   # فواتير المورد، المطابقة الثلاثية، الاستثناءات، الترحيل
    ├── documents/          # مرفقات بإصدارات وبصمة رقمية
    ├── audit/              # سجل تدقيق غير قابل للتعديل
    ├── intake/             # منفذ استخراج AI + Inbox الرسائل
    ├── whatsapp/           # Webhook واتساب مع التحقق من التوقيع
    ├── integrations/       # عقد ERPConnector + موصل التصدير الآمن + الـHub
    └── notifications/       # منفذ التنبيهات (stub)
```

## حالات الطلب

```text
DRAFT → NEEDS_INFORMATION → TECHNICALLY_VALIDATED → SOURCING → QUOTATIONS_RECEIVED
→ PENDING_GM_APPROVAL → APPROVED → PO_ISSUED → PAYMENT_PENDING / DELIVERY_PENDING
→ PARTIALLY_RECEIVED / RECEIVED → QC_HOLD / REJECTED / ACCEPTED
→ INVOICE_PENDING → MATCHING → EXCEPTION / READY_TO_POST
→ POSTED_TO_ERP → PAID_OR_RECONCILED → CLOSED
```

لا يُسمح بالقفز بين الحالات؛ كل انتقال يمر عبر `assert_transition` مع حراس أعمال (اعتماد ساري، استلام مقبول، نتيجة مطابقة).

## نتائج المطابقة

`MATCHED` | `QTY_EXCEPTION` | `PRICE_EXCEPTION` | `TAX_EXCEPTION` | `MISSING_RECEIPT` | `DUPLICATE_INVOICE` | `UNLINKED`

## المرحلة الثالثة: التصنيع والتكلفة الفعلية (مضافة)

- **BoM بإصدارات معتمدة:** قائمة مواد لكل وحدة إنتاج، واعتمادها للمدير العام/المالي؛ **مرجع الانحراف هو أحدث إصدار معتمد فقط** — نسخة مسودة جديدة لا تغير خط الأساس (مختبر).
- **أوامر التصنيع والعمل:** توليد تلقائي من قوالب المراحل حسب المسار — 11 مرحلة لـFrameCAD و10 للحاوية — بتبعيات تسلسلية: لا تبدأ مرحلة قبل انتهاء سابقتها (مفروض في الخدمة ومختبر).
- **تقارير Progress اليومية:** نسبة الإنجاز، عدد العمال، الساعات (ساعات أشخاص: 4 فنيين × 7 ساعات = 28)، والتوقفات بأسبابها. تكلفة العمالة = الساعات × سعر مركز العمل (أو المعدل الافتراضي المُعدّ) — بدون سعر معروف تُسجل صفراً مع علم `labor_rate_missing` ولا يُخترع رقم.
- **نقص المواد أثناء الإنتاج:** تقرير Progress مع علم النقص ينشئ طلب مادة مرتبطاً بالوحدة (`priority=STOPPING`, `channel=progress`) بدل خلط ملاحظة الإنتاج بأمر شراء.
- **صرف المواد للوحدة:** من كميات الاستلام المقبولة (المستبعد منها المحجور جودةً QC_HOLD)، وبسعر أمر الشراء (تقييم مبدئي `provisional_po_price` حتى تسوية الفاتورة، والعملات المختلطة تُعلَّم ولا تُجمع بصمت) — والكميات السالبة ووحدات القياس المخالفة والصرف الزائد عن المتاح مرفوضة (مختبرة).
- **التكلفة الفعلية للوحدة:** مواد فعلية + عمالة فعلية + تكاليف غير مباشرة بنسبة قابلة للإعداد، مع الانحراف مقابل BoM لكل مكوّن.
- **اللوحات:** `GET /dashboards/factory` (تقدم الوحدات، المراحل المتوقفة، ساعات العمل والتوقفات، النواقص) و`GET /dashboards/costs` (انحراف كل وحدة عن BoM) — معروضة أيضاً في الواجهة العربية.

### إضافات التشغيل

- **الشحن والجمارك للحاويات:** إنشاء مسودة بمرجع مستند فريد ومبالغ بالريال، ثم توزيعها بالتساوي أو حسب وزن/قيمة موثقة يُدخلها الموظف. يحفظ النظام مبالغ السنتات دون فقد فروق التقريب، ويمنع تكرار المستند أو المستفيد، ويُظهر التكلفة على الوحدة فقط بعد اعتماد مدير عام أو مالي مختلف عن مُعدّ التوزيع. `GET/POST /api/v1/landed-costs` ثم `POST /api/v1/landed-costs/{id}/approve`. لا يُنشأ قيد ERP تلقائياً.
- **إدارة مراكز العمل:** شاشة عربية في `/operations` لإنشاء المراكز وتعديل سعر ساعة الشخص وتعطيلها، مع إصدارات منع تعارض التعديل وسجل تدقيق قبل/بعد. يستطيع المهندس ربط مرحلة لم تبدأ بمركز نشط وساعات تقديرية. السعر الجديد يُطبّق على الأحداث الجديدة فقط؛ الساعات السابقة تحتفظ بالسعر المسجل وقت التقرير.
- **تقرير تقدم أسبوعي:** في `/operations` و`GET /api/v1/reports/weekly?week_start=YYYY-MM-DD` أو `/api/v1/reports/weekly.csv`. تبدأ الفترة يوم الاثنين وتشمل الأحد، ويمكن تصفيتها بالوحدة أو المشروع؛ تعرض متوسط تقدم مراحل أوامر العمل غير الموزون بداية الفترة ونهايتها، ساعات الأشخاص، تكلفة العمالة، التوقفات، وبلاغات النقص المؤرخة داخل الفترة فقط. تنزيل CSV يدوي وبترميز UTF-8 مع منع صيغ الجداول من أسماء الوحدات.
- **الترحيلات:** ترحيلان إضافيان بعد الإصدار السابق `8d7f8177e403`، مع اختبار ترقية لقاعدة تحتوي مراكز عمل ومستخدمين سابقين، و`alembic check`.

## حدود النسخة الحالية وما بعدها

هذه **نسخة أولية (prototype) عاملة** تنفذ جوهر المرحلتين الأولى والثانية من المخطط (المشتريات + الاستلام والحسابات) مع منافذ جاهزة لما بعدها — وليست النظام الكامل. ما يلي لم يكتمل بعد:

- **مصادقة إنتاجية:** وضع التطوير يستخدم `X-User` (يُعطَّل تلقائياً مع `DEV_MODE=false`)؛ الاستبدال المطلوب هو OIDC (Keycloak/Auth0/Entra) + MFA للموافقين والمحاسبين.
- **AI حقيقي:** منفذ `MaterialRequestExtractor` جاهز لربط مزود OCR/LLM (الافتراضي محافظ لا يخترع بيانات). استخراج الكوتيشنات والفواتير غير مربوط بعد.
- **واتساب:** الـWebhook جاهز بالتوقيع والـIdempotency (والتوقيع إلزامي خارج وضع التطوير)؛ يتطلب رقم WhatsApp Business رسمي وربط أرقام المستخدمين.
- **موصلات ERP:** العقد (`ERPConnector`) معرف وموصل التصدير الآمن يعمل؛ موصل Odoo عبر JSON-2 API هو التالي، وتأكيدات الترحيل تُقبل فقط عبر Webhook موقّع بسر مشترك (`X-ERP-Webhook-Secret`).
- **دورات حياة مستقلة للعمليات المتوازية:** الفواتير الجزئية والدفعات المتزامنة على نفس الطلب تحتاج فصل دورة الطلب عن دورات الدفع/الاستلام/الفاتورة بشكل كامل — التصميم الحالي يغطي المسار المتسلسل المختبر فقط، وهذا من أولويات التطوير التالي.
- **الاستلام مقابل بنود أمر الشراء:** التحقق التلقائي من كميات الاستلام مقابل بنود الـPO ووحدات القياس ومعاملات التحويل لم يُطبق بعد (الكميات تُدخل يدوياً وتُدقّق عند المطابقة).
- **Idempotency:** يُخزن الرد في نفس عملية القيد، لكن الالتزام الذري الكامل (commit واحد للأمر المالي وسجل الرد) يحتاج إعادة هيكلة الخدمات لإزالة الـcommit الداخلي — موثق كتحسين.
- **المرحلة الثالثة — المتبقي:** ربط مستندات الشحن الأصلية وتقييمها تلقائياً، ربط فاتورة المورد لتسوية تكلفة المواد المبدئية بسعر الفاتورة، والتحويل المعتمد بين العملات. التقارير أسبوعية عند الطلب، ولا تتضمن إشعارات مجدولة أو لقطات فترة محاسبية مقفلة.
- **حدود الموافقات:** `APPROVAL_THRESHOLD_1/2` غير مضبوطة افتراضياً — فوق الحد الأعلى يتطلب الكود موافقتي المدير العام + المدير المالي، والقيم تُضبط قبل الإنتاج ولا يخترعها النظام.
