# تسوية المواد والمصاريف والإقفال المالي

ينفذ الإصدار البنود الثلاثة بالترتيب: تسوية تكلفة المواد بفواتير المورد، ثم دفتر المصاريف المباشرة والمعدات، ثم الإقفال المالي وإعادة الفتح. هذه خدمات تكلفة داخلية بعملة SAR؛ لا ترسل قيوداً أو مدفوعات إلى ERP خارجي.

## تسوية المواد بالفواتير

- **المصدر:** فاتورة مطابقة أو باستثناء معتمد من المورد نفسه ولـPO بعملة SAR. حالات المصدر المسموحة READY_TO_POST وEXPORTED وPOSTED_TO_ERP وPAID_OR_RECONCILED.
- **الاعتماد:** يعدها المحاسب أو المالي، ويعتمدها المدير العام أو المالي بخلاف المُعد. المسودة لا تغير التكلفة، ولا يسمح بتسويتين للفاتورة نفسها أو اعتماد مكرر.
- **التحقق:** يعاد فحص البنود عند الاعتماد. تغير المصدر أو اختلاف وحدة القياس أو تجاوز الكمية المقبولة يرفض، حتى لو سبق اعتماد استثناء للفاتورة.
- **السياسة:** المتوسط المرجح لفروق أسعار البنود على الكمية المقبولة، وليس FIFO. توزع الفروق بالسنت على الوحدات المصروف لها والمخزون المتبقي، بطريقة أكبر باقي للفروق الموجبة والسالبة.
- **الفواتير الجزئية:** تبقى الكمية غير المسواة بسعر PO. تتحول `valuation` إلى `settled_invoice_price` عند تغطية كامل الكمية المقبولة لكل مادة مصروفة للوحدة.
- **عدم الازدواج:** لا تدخل الضريبة أو charges أو إجمالي الفاتورة في فرق سعر المادة تلقائياً. المصروف الإضافي يسجل مرة واحدة في مصدره المناسب.
- **مثال:** استلام 120 بسعر PO يساوي 92، وصرف 100، ثم تسوية 120 بسعر 100: فرق إجمالي 960 ريالاً، منه 800 للوحدة و160 لمخزون 20. تصبح مواد الوحدة 10,000 بدلاً من 9,200، لا إجمالي الفاتورة شامل الضريبة.
- **الصرف اللاحق:** يعكس الملخص التسوية المعتمدة للكمية الجديدة دون تحميل مكرر، مع حفظ السنتات التي سبق تثبيتها لوحدة مقفلة.

## المصاريف المباشرة والمعدات

- **المدخلات:** الوحدة، مرجع مستند فريد، DIRECT أو EQUIPMENT، وصف وتاريخ وصافي موجب وضريبة غير قابلة للاسترداد اختيارية وغير سالبة.
- **الدقة:** تخزن الأموال بالسنت الصحيح. ترفض الكسور فوق منزلتين وNaN والصافي الصفري أو السالب والعملات غير SAR.
- **فصل الصلاحيات:** إعداد للمحاسب/المالي واعتماد للمدير العام/المالي بخلاف المُعد. المسودات والملغاة لا تدخل التكلفة.
- **المراجع:** يمنع تكرار المرجع في الدفتر، ويفحص مقابل مراجع الشحن والجمارك في الاتجاهين. يبقى التحقق البشري ضرورياً لاكتشاف المصروف نفسه بمراجع مختلفة.
- **الإلغاء:** تلغى المسودة مع سبب وتدقيق، ولا تحذف. المصروف المعتمد غير قابل للإلغاء أو التعديل المباشر؛ القيود العكسية ليست ضمن الإصدار.
- **المعادلة:** مواد بعد التسوية + عمالة + تحميل غير مباشر على المواد والعمالة + شحن وجمارك معتمدان + مصاريف مباشرة + معدات. لا يطبق تحميل إضافي تلقائي على دفتر المصاريف.

## الإقفال المالي وإعادة الفتح

- **الفحص:** يعرض التكلفة وبصمتها وموانع الإقفال دون تنفيذ أي إقفال.
- **الشروط:** إنتاج وأوامر تصنيع وعمل مكتملة، وBoM معتمدة، وعمالة مسعرة، ومواد مسواة بالكامل، وعدم وجود تكلفة تحتاج تحويل عملة. يلزم ضبط التحميل غير المباشر صراحة ولو بصفر.
- **المصادر:** يمنع الإقفال مع مسودات مصاريف أو شحن أو تسويات، أو فواتير غير مطابقة/غير مسواة. يمنع غياب صرف المواد عند وجود مواد مقدرة بقيمة موجبة.
- **الإجراء:** للمدير العام أو المالي مع مذكرة و`expected_summary_hash`. يعاد حساب التكلفة تحت أقفال المعاملة؛ المراجعة القديمة ترفض، والطلبان المتزامنان لا ينشئان إصدارين.
- **اللقطة:** تحفظ التكاليف والتقديرات والمصادر في JSON مع SHA-256 وإصدار ومستخدم وتاريخ. قراءة ملخص التكلفة بعد الإقفال ترجع اللقطة ولا تتأثر بتعديل التحميل أو سعر المركز لاحقاً.
- **الحماية:** تمنع تغييرات BoM والتصنيع والتقدم والخطة والصرف والمصاريف والشحن والتسويات بعد الإقفال. تغييرات فواتير واستلام PO مستخدم بوحدة مقفلة تتطلب إعادة فتحها.
- **المخزون المشترك:** لا يمنع إقفال وحدة صرف المخزون المتبقي لوحدة أخرى مفتوحة. تبقى حصة الوحدة المقفلة من سنتات التسوية ثابتة.
- **إعادة الفتح:** لمدير عام أو مالي غير منفذ الإقفال، مع سبب ومعرف الإقفال النشط. لا تحذف اللقطة القديمة، وينشأ إصدار جديد عند الإقفال التالي.
- **البصمة:** ترفض قراءة لقطة غير مطابقة لبصمتها. ليست البصمة توقيعاً خارجياً أو بديلاً لحماية قاعدة البيانات من مسؤول خبيث.

## الواجهات

| الإجراء | الواجهة |
|---|---|
| الفواتير المؤهلة | `GET /api/v1/material-settlements/candidates` |
| عرض/إعداد التسويات | `GET/POST /api/v1/material-settlements` |
| اعتماد تسوية | `POST /api/v1/material-settlements/{id}/approve` |
| عرض/إعداد المصاريف | `GET/POST /api/v1/unit-expenses` |
| اعتماد/إلغاء مسودة مصروف | `POST /api/v1/unit-expenses/{id}/approve` أو `/cancel` |
| فحص الإقفال | `GET /api/v1/production-units/{id}/financial-close/check` |
| تنفيذ الإقفال | `POST /api/v1/production-units/{id}/financial-close` |
| التاريخ واللقطات | `GET /api/v1/production-units/{id}/financial-close` |
| إعادة الفتح | `POST /api/v1/production-units/{id}/financial-close/reopen` |

الإعداد للتسوية يأخذ `invoice_id`، والاعتمادات تأخذ `note`. الإقفال يأخذ `note` و`expected_summary_hash` من الفحص، وإعادة الفتح تأخذ `note` و`close_id` الحالي.

الواجهة العربية في `/operations`، تبويب **التكلفة والإقفال**، توفر الإعداد والاعتماد والمصاريف وفحص الموانع والتكلفة وتاريخ اللقطات والإقفال وإعادة الفتح بتأكيد صريح. تسجيل الفواتير ومطابقتها وإدخال التصنيع التفصيلي ما زال عبر API، وليس عبر شاشة ERP مكتملة.

## الترقية

توجد ثلاثة ترحيلات متتابعة بعد `7782486e6459`: التسويات `359923f82280`، والمصاريف `b4f7f1a7a09a`، والإقفال `fd576b49f08f`.

للقاعدة المدارة بـAlembic، خذ نسخة احتياطية ثم:

```bash
python -m alembic upgrade head
python -m alembic check
```

لا تستخدم `stamp head` عشوائياً لقاعدة أنشئت بـ`create_all`. التراجع يحذف جداول المرحلة المتراجع عنها، ويستخدم هنا في الاختبار بقاعدة معزولة.

## الاختبار

نتيجة التحقق النهائية في 2026-10-15: **104 اختبارات خادم ناجحة، صفر فشل**، في 274.18 ثانية. نجحت أيضاً اختبارات الواجهة السابقة الخمسة عشر، ومسار متصفح حقيقي مستقل بثمانية فحوص مترابطة، دون أخطاء JavaScript أو تجاوز أفقي للمستند بالعروض المفحوصة.

نجح `alembic upgrade head` و`alembic check` دون اختلاف مخطط، واختبار الترقية من قاعدة سابقة تحتوي بيانات والتراجع وإعادة الترقية ضمن مجموعة الخادم. نجح أيضاً تجميع Python وفحص صياغة JavaScript و`git diff --check`.

بعد تحديث رابط المعاينة نفسه، نجح فتح التبويب وفحص موانع إقفال الوحدة التجريبية غير المكتملة وتعطيل الإقفال، دون أخطاء JavaScript أو طلبات تعديل. أُعيد الفحص داخل iframe معزول دون `allow-same-origin` ونجح كذلك؛ لا توجد كتابة مالية على قاعدة المعاينة ضمن هذا الفحص.

```bash
python -m pytest tests/ -q
```

تغطي المجموعة التسوية الكاملة والجزئية والسالبة، والسنتات والمخزون، والصلاحيات والتكرار وتغير المصدر والكميات المتداخلة، والمصاريف والضريبة والمدخلات غير الصالحة، والإقفال المتزامن وبصمة مراجعة قديمة، وإعادة الفتح والإصدار الثاني وثبات اللقطة وكشف العبث.

السيناريو المترابط يعاد داخل التطبيق وعبر HTTP فعلي بقاعدة معزولة: مواد 10,000 + عمالة 385 + تحميل 10% بقيمة 1,038.50 + معدات وضريبة غير مستردة 105.01 = **11,528.51 ريالاً**. بعد إعادة الفتح واعتماد مصروف مباشر 10 يصبح الإصدار الثاني **11,538.51**، مع بقاء الأول دون تعديل.

اختبار المتصفح `tests/browser/finance.mjs` يكتب بيانات تجريبية ويرفض غير `127.0.0.1:8770`. شغل خادم اختبار منفصلاً بقاعدة جديدة تماماً و`OVERHEAD_PCT=10`، لا قاعدة المعاينة المشتركة، ثم:

```bash
python -m tests.browser.seed_finance_qa
cd tests/browser
node finance.mjs
```

ترفض التهيئة قاعدة فيها وحدات مسبقاً. يتحقق المتصفح من إعداد التسوية والمعدات والضريبة والاعتماد، وإلغاء تأكيد الإقفال دون طلب مالي، ثم الإقفال وإعادة الفتح والإصدار الثاني، والتاريخ وصلاحيات المستودع وعروض 320 و390 و768 و1440 والوضع الداكن.

## حدود باقية

- **العملة والتصحيحات:** SAR فقط، وفواتير كميات موجبة. فروق العملات والإشعارات الدائنة والمرتجعات والقيود العكسية تحتاج دورة مستقلة.
- **المستندات الخاطئة:** لا يتجاوز مصدر غير صالح الحماية باعتماد استثناء. يلزم تصحيحه؛ لا توجد هنا واجهة تعديل/إلغاء فاتورة مورّد أو إعادة تجهيز تسوية من مصدر مصحح.
- **المحاسبة:** دفتر تكلفة داخلي، لا قيد ERP ولا إقفال فترة محاسبية أو تحقق اكتمال الدفع.
- **الإنتاج:** إعادة الفتح المالي لا تعيد فتح إنتاج DONE ولا تضيف دورة تصحيح كميات مقفلة أو اعتماد جودة نهائي.
- **الضريبة:** أهلية الاسترداد يقررها المحاسب؛ الضريبة غير المستردة مدخل صريح.
- **إعادة الإرسال:** المراجع الفريدة والاعتماد الأحادي ليسا Idempotency-Key عامة لجميع الإجراءات.
- **الخط الأساسي:** التقديرات قبل الإقفال ما زالت بأحدث BoM وأسعار المراكز الحالية، وتثبت عند الإقفال لا عند إنشاء MO.
- **التشغيل:** X-User تطويري. يلزم OIDC/MFA ونسخ احتياطي وصلاحيات واختبار PostgreSQL فعلي قبل بيانات حقيقية. الاختبار هنا على SQLite، ولا يتضمن تحميل إنتاج أو اختبار اختراق.
